# 链路 ② 铺货上架

> 目标：把一个选好的商品，铺到电商平台上架，再关联落地页，最后录入广告平台的商品库。
> 关键词：跨系统集成、主键贯穿、先删后填、兜底规则、分级自动化

---

## 一、链路总览

```
货源系统 ──铺货──▶ 电商平台 ──────────────▶ 落地页中转系统 ──────▶ 广告商品库
   （货盘）        （商品上架、取主图、            （用商品ID关联，        （业务单元/店铺/类目/
                    取商品ID）                     产出 3 条落地页）        主图/属性/落地页）
                                                        │
                                                        └── 3 条落地页链接 ──▶ 广告商品库 3 个输入框
                                                                              （顺序必须一一对应）
```

**4 个系统、约 24 个操作步骤，全程靠"复制粘贴 + 跨系统核对"串联。** 这是最典型的"单步都不难、整体极耗时且极易错"的链路。

---

## 二、流程分解

### 阶段 A · 电商平台（取两样东西）

| 步骤 | 产出 |
|---|---|
| 商品列表 → 搜**货源系统里的商品全名** → 图片详情下载 | 主图原图 |
| 转 **800×800** | 广告商品库要求的主图规格 |
| 复制**商品 ID** | 后续关联的次键 |

### 阶段 B · 落地页中转系统（用商品 ID 关联）

| 步骤 | 规则 |
|---|---|
| 选平台 → 添加商品 → 粘贴商品 ID → 上架 | 平台必须与阶段 A 一致 |
| 点击商品旁的平台入口 | 得到 **3 条落地页链接** |

### 阶段 C · 广告商品库（录入）

| 字段 | 值 / 规则 |
|---|---|
| 业务单元 | 固定常量 |
| 店铺 | 固定常量 |
| 类目 | 按商品全名理解归类 |
| 品牌 | **固定值「无」** |
| 商品名 | **固定格式** `{前缀}-{平台码}-{商品全名}` |
| 主图 | 阶段 A 转好的 800×800 |
| 商品属性 | 按图片/全名理解填写；**无对应项 → 直接选第一个**（兜底规则） |
| 动态商品广告信息 | 🚫 **不动作区，保持默认** |
| 落地页 | 跳转类型选**小程序**；**3 个输入框分别填 3 条链接，顺序与上一阶段一一对应** |
| 提交 | 完成 |

---

## 三、设计要素

### 1. 主键贯穿：全名与 ID 分工

| 标识 | 作用 | 贯穿范围 |
|---|---|---|
| **商品全名** | **业务主键** | 货源系统 → 电商平台 → 广告商品库 |
| **商品 ID** | **技术次键** | 电商平台 ↔ 落地页中转系统 ↔ 素材库 |

两个标识各司其职，不混用：**全名保证"找得到同一个品"，ID 保证"关联得准"。**

### 2. 3 条落地页 = 最容易出错的点

一次上架产出 **3 条不同的落地页链接**，必须在两个系统里各填一次、**顺序一一对应**。

**它同时是全局唯一的"多值一致性"风险点**——其余字段都是单值常量或单值生成，只有这里是"一组值跨系统保持顺序一致"。自动化必须把它当成一次事务处理，不能逐条独立填。

### 3. 兜底规则：宁可填默认值，也不让流程中断

**商品属性无对应项 → 直接选第一个。**

这是自动化能不能端到端跑通的分水岭：只要有一处"卡住等人来看"，整条链路就退化成"AI 填一半、人补一半"。

### 4. 分级自动化：按影响面决定精度

**这是本链路最有价值的设计判断。**

关键事实：**广告商品库是内部中间层——只用于关联广告，终端用户看不到它。**

| 环节 | 下游影响 | 策略 |
|---|---|---|
| 类目、商品属性 | **低**（内部层、选错不阻断，强行继续即可） | 🟢 **全自动，允许宽松判断** |
| 主图、商品名、落地页链接 | **高**（直接影响投放跳转） | 🟡 **严格按常量格式执行** |
| 动态商品广告信息 | 不可触碰 | 🔴 **禁改，保持默认** |
| 各后台登录验证 | 安全边界 | ⛔ **必须人工** |
| 出价、投放开关 | 直接花钱 | ⛔ **必须人工确认** |

> **如果不做这个「影响面评估」**，最保险的做法是每个字段都请求人工确认——那这条链路就永远无法端到端自动化。**"判断哪里可以松、哪里必须严"，本身就是核心设计工作。**

### 5. 认证边界

三个后台的登录验证**全部由人工完成**，验证后才交给 Agent 操作。

- Agent 只操作**已登录会话**，不接触任何账号凭证与验证码
- 这既是技术现实（验证码无法自动化），也是安全设计里最核心的一条原则

### 6. 异常上抛：不在本环节硬扛

| 场景 | 处置 |
|---|---|
| 搜不到商品全名（商品未铺过去） | **回上游货源系统人工重新铺货**，再重跑本链路 |
| 类目选错 | 不阻断，强行继续（低影响） |

**原则：异常往上游抛，不在当前环节做局部修补。** 局部修补会产生"这条记录和其他记录不一致"的隐性债务。

---

## 四、异常与边界

| 场景 | 处置 |
|---|---|
| 全名搜不到商品 | 回货源系统重新铺货（异常上抛） |
| 落地页链接数量不足 3 条 | 中止本商品，回报（多值一致性不能将就） |
| 类目/属性判断不确定 | 类目按宽松理解填、属性无对应选第一个 |
| 某后台登录态失效 | 人工重新登录 |

---

## 五、效率

| 指标 | 数值 |
|---|---|
| 人工耗时 | **约 6–8 分钟/品** |
| 覆盖系统数 | 4 |
| 操作步骤数 | 约 24 |
| 唯一需要"理解"的环节 | **2 处**（类目、商品属性） |
